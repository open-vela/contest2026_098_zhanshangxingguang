## 二、需要补的缺口

### ✅ A.（已解决 2026-08-14）PSRAM 纳入可用内存 —— 但用的是独立堆，不是 `mm_addregion`

**原判断**：`CONFIG_MM_REGIONS` 默认 1，堆只有 336K AP SRAM，PSRAM（`0x60000000`）完全没进堆，
双屏 framebuffer + 摄像头缓冲（GC2145 `640×480 YUYV = 614KB`）放不进 336K。

**实际实现（S1–S3 分阶段完成，全部实机验证）**：

| 阶段 | 内容 | 实测结果 |
|---|---|---|
| S1 | PSRAM 控制器初始化（电源树/时钟/SF reset/bypass/颗粒 MR 配置）+ ID 识别 + 单字数据通路自检 | `ID=0x8d08`（APS128XXO **16MB**）、`data path OK (0x60000000 verified)` |
| S2 | 全范围读写、地址别名检测、访问宽度测试 | **16MB 全范围 4194304 words 零错误**；无别名；**8/16/32 位全可用**（16 位可用 → RGB565 安全） |
| S3 | 独立 PSRAM 堆 + 显式 API | `arena 16384 KB`；`alloc 1024`→`0x60000178`；`alloc 614`→`0x60100180`；已用量 `1638 KB = 1024+614` 精确吻合；`freeall` 后完全回落无碎片 |

**⚠️ 与原建议的偏离（重要，答辩会被问）**：**没有**采用 `CONFIG_MM_REGIONS=2` + `mm_addregion()`
把 PSRAM 并入主堆，而是用 `mm_initialize()` 建了**独立 PSRAM 堆**，对外暴露
`bk7258_psram_malloc/calloc/free/meminfo`（类比 ESP32 的 `heap_caps_malloc(MALLOC_CAP_SPIRAM)`）。

原因是实测带宽（见下）：**CPU 32 位访问 PSRAM 约 11.3/8.5 MB/s（写/读）、逐字节仅 4.0/3.5 MB/s，
比 SRAM 慢一个量级**。若并入主堆，
`malloc()` 会不加区分地把小对象分配到 PSRAM 上，造成难以定位的整体性能退化。
独立堆保证普通 `malloc()` 仍走快速 SRAM —— 已用实测证明：`malloc(1024)=0x2801c5a8 (SRAM OK)`。

**cache 一致性**：当前 defconfig 无 `CONFIG_ARMV8M_DCACHE`，D-cache 关闭，本阶段无需 clean/invalidate。
⚠️ 但**一旦启用 D-cache，DMA 写入 PSRAM 后必须 invalidate**，否则 CPU 读到旧数据。已记入代码注释。

### 📊 PSRAM 带宽实测与由此确定的架构决策（本轮最有价值的产出）

> ⚠️ **2026-08-14 数据更正**：本节此前记的「写 1768 KB/s、读 1802 KB/s（约 1.8 MB/s）」
> **是无效数据，已作废**。原因是当时**系统 tick 从未使能** —— `up_timer_set_lowerhalf()` 在
> `CONFIG_TIMER_ARCH` 未开时是空宏，把 `systick_initialize()` 调用连参数一起被预处理器丢掉，
> 于是所有 `clock_systime_ticks()` 差值恒为 0，算出来的"带宽"没有意义。
> 修好 SysTick、并把 CPU 主频从错标的 480MHz 校准到实测 120MHz 之后，重测得到下表。

**重测结果**（2026-08-14，SysTick 修复 + 主频校准后）：

| 访问方式 | 写 | 读 | 测试条件 |
|---|---|---|---|
| **32 位字**（`psram test 16`） | **11.3 MB/s**（11619.8 KB/s） | **8.5 MB/s**（8668.7 KB/s） | 16MB 全范围、4194304 words、**0 错误**、3.30 s |
| **8 位字节**（`psram fbtest`） | **4.0–4.3 MB/s** | **3.5 MB/s** | 614KB×2、32/64 字节对齐各一轮 |

三点解读：

1. **访问宽度影响巨大**：32 位访问吞吐是 8 位的 2.4–2.7 倍 —— 每次总线事务的固定开销远大于
   数据本身，所以**逐字节 memcpy 是最差写法**，能用 32 位就用 32 位。
2. 这仍是**最坏情况**：CPU 逐个 `volatile` 访问、无 D-cache、无 burst。DMA + burst 会更高。
   准确表述是「**CPU 逐字访问 PSRAM 比 SRAM 慢一个量级，真实带宽要靠 DMA 才能拿到**」，
   而不是「PSRAM 慢」。
3. 换算成**帧时间**，这才是决策依据：

| 用途 | 大小 | CPU 全量读耗时 @8.5MB/s | 归属 | 理由 |
|---|---|---|---|---|
| 单眼 LCD 缓冲（160×160 RGB565） | 50 KB | 5.9 ms | **留 SRAM** | — |
| 双眼 LCD 单缓冲 | 100 KB | **11.8 ms** | **留 SRAM** | 30fps 预算 33ms，光"把像素读出来"就吃掉 36%，还没算 LVGL 渲染的读改写；100KB 在 336K SRAM 放得下 |
| 双眼 LCD 双缓冲 | 200 KB | 23.6 ms | **留 SRAM** | 同上（偏紧但可行） |
| GC2145 `640×480 YUYV` 一帧 | 614 KB | 72 ms | **放 PSRAM** | **336K SRAM 根本放不下**，容量硬约束，与快慢无关 |
| GC2145 `320×240 YUYV` 一帧 | 154 KB | 18 ms | **放 PSRAM** | AI 推理建议用这一档，见下 |

→ **结论不变，但依据换成了帧时间：LCD 帧缓冲留 SRAM，PSRAM 专供摄像头大缓冲。**
LCD 侧是"能放进 SRAM 就别去 PSRAM 交 12ms/帧的过路费"，摄像头侧是"614KB 在 SRAM 里放不下"。
这也是原计划"把 LCD 帧缓冲迁到 PSRAM"的**修正**。

→ **对摄像头链路的新约束**（由 8.5 MB/s 读推出）：全帧 640×480 每做一次 CPU 遍历要 72 ms，
即**全帧 CPU 处理的天花板约 14 fps**。所以 AI 推理不要按 30fps 全帧扫，应当
① DVP 侧直接出 320×240（154KB / 18ms），或 ② 只处理 ROI，或 ③ 降推理帧率到 5–10 fps。
这条要在 M3 摄像头移植时当作设计前提，而不是等跑不动了再回头改。

**遗留（S4 处理）**：`mm_malloc` 只保证 8 字节对齐（实测首块 `0x60000178`），而 DVP DMA 通常
要求 32/64 字节对齐 → 需补 `bk7258_psram_memalign()`，否则摄像头移植时会踩坑。

### 🟡 B. `BOARD_PSRAM_SIZE` 可能填错（8MB vs 16MB）
- `board.h` 写 `BOARD_PSRAM_SIZE = (8 * 1024 * 1024)`。
- 但调试日志（`DEBUG_JOURNAL_zh-cn.md:698`）里原厂固件打印：
  ```
  psram:W(10):psram type(16MB) not match CONFIG_PSRAM_CAPACITY 0X00800000
  ```
  → **实测芯片报 16MB**，原厂配置写的才是 8MB。

**✅ 已解决（2026-08-14）**：S1 实机读回 `ID=0x8d08`（= `PSRAM_APS128XXO_OB9_ID`，对应 **16MB**），
S2 全范围 16MB 读写零错误 + 别名检测确认 16MB 真实可寻址。
`board.h` 已改为 `BOARD_PSRAM_SIZE = (16 * 1024 * 1024)`，并在注释里写明
"Measured: ID=0x8d08 (APS128XXO 16MB)，原值 8MB 有误"，避免以后再被原厂默认值带偏。

## 四、结论（2026-08-14 更新）

最小系统本身**没有配置遗漏**，基线 Checklist 全通过，L0 阶段已收尾。

原文标记的头号阻塞项——**PSRAM 未纳入堆**——现已解决：16MB 全范围验证通过、独立堆可用、
614KB 摄像头帧可分配、主堆未被污染。M2（双屏）已完成，M3（摄像头）的内存前提已就绪。

本轮额外收获一个由实测数据支撑的架构决策：**帧缓冲留 SRAM、PSRAM 专供摄像头**
（依据：双眼 100KB 帧缓冲若放 PSRAM，仅"读出来"就要 11.8ms/帧、占 30fps 预算 36%；
而 614KB 摄像头帧在 336K SRAM 里放不下 —— 前者是性能取舍，后者是容量硬约束）。
这比单纯"我们支持了 PSRAM"更有说服力，建议在答辩中作为工程判断的例证。

另一个同样值得讲的产出：**发现并修复了「系统 tick 从未使能」** —— 一个空宏把
`systick_initialize()` 连参数一起吃掉，系统照常启动、NSH 照常可用，只有 `sleep` 挂死和
"带宽恒为 0"两个症状。这类"看起来完整、实际被预处理器删掉"的缺陷很典型，
也说明**任何性能数字都必须先验证时间基准**。
