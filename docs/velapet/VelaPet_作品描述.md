# VelaPet —— 端侧 AI 情感陪伴机器人（openvela × BK7258）

> 备选名：灵伴 / VelaCompanion / 小维。以双圆屏为"眼睛"、摄像头为"眼睛看世界"，
> 做一个**断网也不变傻**的桌面 AI 情感陪伴机器人。

## ① 项目名称与一句话定位

**VelaPet —— 端侧 AI 情感陪伴机器人**。

用 BK7258 的双圆形 LCD 做拟人"双眼"、摄像头做视觉感知，在**完全离线、数据不出设备**的前提下完成"看得懂表情、对得上眼神、听得懂指令、还会关心你身体"的陪伴闭环。对标市面 AI 玩具机器狗，但把它们"必须联网、离线即失智、隐私上云"的短板反过来做成卖点——**端侧离线 AI + 健康关怀 + openvela 新板生态贡献**。

## ② 目标开发板及选板理由

目标板：**BK7258 DevKit**（博通集成 BK7258，双核 480MHz ARMv8-M Wi-Fi 6 AI-SoC；本作品完成其 openvela 首次适配）。**该板是本届 openvela 大赛官方「待适配开发板」，正对应「新硬件平台适配」赛道（组委会重点加分方向）。**

实测板载能力（据官方原理图与方框图「BK7258 AI Demo」V1.0，详见 ⑪ 实测清单）：**双 160×160 圆屏**（QSPI0 / QSPI1）、**GC2145 摄像头**（2MP DVP）、**双麦克风**、**SC7A20H 三轴加速度计**（支持睡眠唤醒）、**震动马达**、**MFRC522 NFC 读卡器**、**SD NAND 1GB**、喇叭 + HT6872 功放、S1–S3 按键、LED×2、锂电池（电量走 ADC0，ETA3422 充电管理）、**CH340 调试串口**、2.4G BLE/WiFi；芯片侧支持 KWS/AEC/NS、G711/G722 与 H.264/MJPEG 硬编解码。

选板理由：

1. **硬件天生适配拟人陪伴**：双 QSPI 圆屏恰好做"两只眼睛"的动态表情，DVP 摄像头做视觉交互，双麦 + 喇叭做语音与左右寻声，加速度计 + 震动马达做体感与触觉反馈，NFC 读卡器做实体养成，LED 做情绪灯效，电池让它成为可随手摆放的桌面伙伴——一块板即可完整演示，无需外挂。
2. **音视频 + AI 能力对口**：BK7258 面向端侧 AI（摄像头/门锁/AI 玩具）场景，硬件 KWS/AEC/NS + H.264 编解码，算力足以实时跑轻量视觉模型（人脸/表情/手势、rPPG）与端侧唤醒。
3. **赛道命中 + 生态价值**：openvela 尚无 BK7258 适配，本作品从内核启动到 QSPI 屏/Camera/Audio/GPIO/I2C(加速度计、NFC) 驱动完成板级 BSP，是可 PR 回 `vendor_beken` 上游、回馈社区的生态贡献。
4. **场景被官方背书**：大赛待适配清单里还有一块「声网 & 博通集成 对话式 AI 开发套件」，明确面向 AI 玩具/陪伴设备、支持单/双屏——说明"博通集成芯片 + 双屏 + AI 陪伴"正是官方设想的落地场景，我们踩在点上。

## ③ 核心功能（逐条含所需硬件能力）

1. **双眼情感表情引擎【招牌】** —— 双圆屏渲染拟人眼神：开心/好奇/困倦/关心/惊讶等动态表情，随交互与对方情绪实时切换。硬件：双圆形 LCD + 背光，LVGL。
2. **视觉多模态交互** —— 摄像头做在位检测、人脸/表情识别、手势识别，并驱动"**眼神跟随**"（视线跟着人脸/手移动）。硬件：板载 DVP 摄像头 + 端侧视觉模型。
3. **离线语音交互** —— 唤醒词统一用大赛指定 **"你好，openvela / Hello，openvela"**，配命令词（"讲个笑话/看看我心率"）；端侧 KWS（芯片硬件支持 KWS/AEC/NS）。硬件：双麦克风 + 喇叭。自由问答为**可选联网**走云端 LLM。
4. **端侧健康关怀（差异化）** —— 摄像头 rPPG 隔空/指尖测心率，识别疲劳/紧张时主动关心并给出提示。硬件：摄像头 + 端侧信号/轻量模型；全离线（该板无 PPG 传感器，反而凸显"摄像头测心率"的创新）。
5. **体感 + 触觉交互（机器宠物感）** —— 板载 SC7A20H 加速度计识别"被拿起/摇晃/轻拍"，做拟人反应（拿起就醒来、摇晃会"晕"、轻拍会开心），震动马达给触觉反馈。硬件：三轴加速度计 + 震动马达。
6. **声光情绪外化** —— 跑马灯 LED + 喇叭配合表情做情绪灯效与音效。硬件：GPIO LED + 音频。
7. **可选云端增强** —— 联网时自由对话（云端 LLM，用官方发放的 Xiaomi MiMo Token 或对接豆包/DeepSeek）、天气/时间查询、OTA。硬件：Wi-Fi。

> 以上外设均已由官方原理图确认为**板载**，无需外挂（详见 ⑪ 硬件实测清单）。

## ④ 各功能技术方案（端侧 / 云端、框架 / SDK）

- **openvela 适配（底座工作项、赛道核心）**：完成 BK7258 的 openvela（NuttX）启动引导 + 至少 UART 控制台，再逐步补齐板级驱动——双 QSPI 屏、Camera（DVP）、Audio（喇叭/双麦）、GPIO/LED、I2C（SC7A20H 加速度计）、NFC（MFRC522）、震动马达、电量 ADC、Wi-Fi/BLE；提交 defconfig + 板级初始化 + 驱动 + 复现说明。借助官方 `nuttx-driver-development` skill / `driver-workflow` agent 加速。
- **表情引擎**：LVGL 双圆屏分屏渲染，状态机驱动眼神动画；情绪由视觉/语音/体感/健康事件经 eventbus 汇聚触发。
- **视觉交互**：端侧轻量人脸检测（tiny detector）+ 表情/手势分类（TFLite Micro / CMSIS-NN，int8 量化）；眼神跟随用人脸框坐标映射到双屏视线。
- **健康关怀 rPPG**：摄像头帧 → ROI → 绿通道/色度 → 带通(0.7–4Hz) → POS/CHROM + FFT 取心率；可选小 1D-CNN 提精度。
- **体感交互**：SC7A20H 加速度计数据经 uORB 订阅 → 规则识别拿起/摇晃/轻拍 → 驱动表情 + 震动马达触觉。
- **语音交互**：端侧唤醒（"你好，openvela"）+ 离线命令词（芯片 KWS/AEC/NS）；自由对话可选云端 LLM（联网时，走 Xiaomi MiMo / 豆包）。
- **通信/同步**：cpc + property/eventbus 做模块间/核间通信；Wi-Fi 走标准网络栈，云端可选 HTTP/MQTT。

## ⑨ 与快应用 service.health 的关系与差异化

> 结论先行：`service.health` 是**快应用赛道**的手表健康接口，与本作品**不冲突、不重叠**；它反而反衬出我们的创新点，且其数据规格可被我们借用。

### 它是什么、为什么不能直接用
- `service.health` 是**手表快应用（JS）**的系统接口（`import health from "@service.health"`），面向 `deviceTypeList: ["watch"]`、圆表盘 `designWidth: 480`，跑在 **AIoT IDE 内置模拟器**（镜像 `vela-miwear-watch-5.0(开发者大赛)`、`aiot-core/aiot-emulator ≥ 1.7.22`），数据为 31 天真人数据 1Hz 回放的 mock。属于「手表应用创新（快应用）」赛道。
- VelaPet 是 **BK7258 上的原生 openvela（C/C++）应用**，设备形态非 watch、无手表健康服务、无 PPG 传感器，因此**无法直接调用 `@service.health`**。二者是不同赛道、不同设备、不同技术栈。

### 差异化（这正是我们的护城河）
| 维度 | 快应用 + service.health | VelaPet（BK7258 原生） |
|---|---|---|
| 赛道 | 手表应用创新（快应用） | 新硬件平台适配（重点）+ AI 硬件产品创新 |
| 设备 | 手表（watch 运行时 + 模拟器） | BK7258 开发板（原生 openvela） |
| 心率来源 | 系统健康服务直接给（有 PPG 传感器） | **无 PPG，摄像头 rPPG 端侧算出** |
| 技术难度 | 订阅一行 JS 即可拿数据 | 从 BSP 移植到端侧视觉推理全链路 |
| 定位 | 读现成数据、做展示卡片 | 在没有传感器的板子上"无中生有"测心率 |

要点：手表上 HR 是"免费"的系统能力；我们在**没有 PPG 传感器**的板子上用摄像头把心率"算出来"，难度与创新点都在——**不因 service.health 的开放而变冗余**。

### 叙事校准（答辩要点）
- 主打「**移植难度 + 情感陪伴**」，把 rPPG / 健康关怀定位为**亮点之一而非全部**，避免被拿去与"三行 JS 拿 HR"的轻量健康 demo 对比。
- 若评委问"手表已经能读健康数据，你的意义"：强调设备/赛道不同 + 无传感器条件下的端侧视觉测心率 + 陪伴机器人的多模态闭环。

### 可借用之处（让 rPPG 演示更可信）
- 采用官方真人数据值域对齐 UI 与阈值：心率 **48–182 bpm**、血氧 **90–99%**、压力 **1–49**，上报节奏 **1Hz**。
- 真机摄像头 rPPG 打通前，可先用这套 mock 风格数据驱动 VelaPet 的表情/曲线做 UI 联调。

### 进阶选做（跨设备组合，暂不主攻）
- VelaPet 作桌面伙伴 + 一个手表快应用用 `service.health` 读**真实 HR**，经 BLE 喂给 VelaPet 显示/关怀 —— 可多占「手表应用创新」方向、故事更完整，但需多做 watch 端与联调，scope 变大，列为后期加分项。

## ⑩ 对标「分布式端侧 AI 桌面宠物 / MiGlow 米灵」（内部黑客松作品）

> 说明：该作品是小米内部黑客马拉松（极客创新单元）参赛作品，与本作品**不在同一赛事**，不构成直接竞争；但它代表了"AI 桌面萌宠"这一赛道的当前最高叙事水平，作为差异化标尺与灵感来源。

### 它的打法（据公开物料）
- **形态**：光学悬浮成像（全息立方体）投影宠物形象。
- **技术**：端侧大模型 + 数据分级、**分布式算力协同**（借手机/其它设备算力）。
- **卖点**：AI 动态形象智能生成（萌宠全网唯一）、**主动感知**（读手机通知/界面/聊天 + 摄像头看情绪）、**带记忆决策**（越用越懂）、**底层硬核联动**（系统底层 + MCP 原子能力，能代劳发微信"下班啦"）、极致隐私（数据不上云）、人车家全生态联动。
- **架构**：感知层 / 记忆层 / 决策层 / 隐私层；宣称三重专利。
- **口号**："不是技术壁垒，而是情感壁垒。"

### 差异对比
| 维度 | 米灵（对标） | VelaPet（本作品） |
|---|---|---|
| 赛事/评价 | 内部黑客松·极客创新 | openvela 公开赛·**新硬件适配（重点加分）** |
| 技术层次 | 应用/智能层（跑在成熟平台上） | **OS/驱动层**：BK7258 首次 openvela BSP 移植 |
| 算力策略 | 端侧大模型 + **分布式协同**（依赖手机等外部算力） | **单板自给**，MCU 级全离线，不依赖任何外部设备 |
| 形态 | 全息投影（**看得见、摸不着**） | 实体双眼 + **可触摸/可养成**（加速度计、震动马达、NFC 读卡） |
| "主动"来源 | **数字世界**事件（手机通知/聊天/日程） | **物理世界**观察（视觉、体感、生理信号） |
| 健康能力 | 无 | **摄像头 rPPG 测心率**（无 PPG 传感器硬件） |
| 成本/可量产 | 全息 + 分布式算力，BOM 高 | MCU 单芯片方案，**BOM 低、易量产** |

### 我们能打的三个空档
1. **它的"主动"依赖手机数字信号；我们的"主动"来自对人的观察。** 久坐、疲劳、心率升高、环境变暗——这些它读不到（投影没有传感器闭环），我们有摄像头 + 加速度计 + rPPG。
2. **它摸不着；我们可以被抚摸、被喂食、会成长。** 实体交互是全息方案的结构性短板。
3. **它需要借算力；我们在一块 MCU 上全离线自给。** 隐私叙事我们更硬——不是"数据不上云"，而是**根本无需其它设备参与**。

### 建议新增的功能（按性价比排序，均为 BK7258 板载能力可达）
> 原则：只加**吃硬件长板 + 强化情感记忆点 + 不威胁移植主线**的功能。移植仍是第一优先级。

- **A. 「转头看你」（推荐，但改走视觉路径）** —— 眼睛跟着人转，全息投影做不到"回头看你"。
  - **基线**：**摄像头人脸跟踪**驱动视线（零额外硬件，摄像头本就要用）。
  - **进阶**：补第二颗麦后做**双麦寻声**（GCC-PHAT/TDOA），实现"听到声音先转头、再用眼睛确认"。
  - ⚠️ 实物只装了 1 颗麦（另一座空置），故寻声**需自行补麦**，不作为关键路径。
- **B. 心跳同步震动（情感杀手锏）** —— rPPG 测到你的心率后，用**震动马达**按同一节律搏动：把它拿起来，它的"心跳"和你同步。技术上只是 rPPG → PWM，情感冲击极强，路演记忆点拉满。
- **C. NFC 实体养成（已确认可做）** —— 板载 **MFRC522** 读卡器（I2C/UART 跳线可选）：碰"食物卡"喂食、碰卡切换用户/模式（专注/睡眠）。把"养成"落到实体交互上，全息方案永远做不到。
- **D. 「认识你」离线人脸识别** —— 端侧轻量 face embedding + 余弦相似度，区分主人/陌生人并给不同反应（对标它的"认识你"，但我们全离线、不借算力）。列为进阶。
- **E. 主动关怀引擎 + 呼吸引导** —— 物理世界触发的主动行为：久坐提醒（加速度计静止判定 + 在位检测 + 计时）、疲劳检测（rPPG 变化 + 眨眼/哈欠）、光线变暗关心休息；检测到紧张时进入**呼吸引导**：双眼按吸气/呼气节奏缩放 + 震动马达打节拍，带你慢下来。
- **F. 个人基线记忆（诚实版"记忆"）** —— 用 **Nand Flash** 存你的作息与心率基线、互动偏好，做**个性化阈值**（异常判定基于"你自己的基线"而非通用阈值，更科学）。明确不吹"端侧大模型记忆"，只讲统计画像 + 个性化，答辩站得住。
- **G. 亲密度成长** —— 抚摸（轻拍）、喂食（NFC）、陪伴时长累积为亲密度，驱动眼神/表情/反应变化，形成长期羁绊。

### 取舍建议（防 scope 失控）
- **本期做**：A（转头看你）+ B（心跳同步）+ E（主动关怀/呼吸引导）—— 三个都吃现有硬件、几乎不增加新驱动，却直接对上它的"主动"与"情感"叙事。
- **有余力再做**：C（NFC 养成）、F（基线记忆）、G（亲密度）。
- **进阶/看时间**：D（人脸识别）。
- **不跟的**：全息投影、分布式算力、端侧大模型、MCP 系统级联动——硬件与赛道都不匹配，跟了反而丢掉我们"单板全离线 + BSP 深度"的优势。

### ⚠️ 160×160 双屏带来的设计约束（重要）
- **好消息**：单屏帧缓冲仅 `160×160×2B ≈ 50KB`，双屏约 100KB —— LVGL 跑得轻，刷新率容易做高，眼神动画会很顺滑；MCU 内存压力小。
- **约束**：屏太小，**放不下精细图表**。原计划的"心率曲线图 / 数据仪表盘"在 160×160 圆屏上会挤成一团。
- **应对**：UI 全面**图形化、去文字化**——
  - 双眼以**风格化眼神**为主（原厂 demo 已验证 160×160 画眼睛效果很好）。
  - 心率不画折线图，改用**眼睛的"心跳律动"**（瞳孔按心率缩放）+ **大号数字**呈现。
  - 状态用**颜色/形状**表达（LED + 眼神色调），而非文字。
  - 需要文字时只显示极短词（"饿了""累了"），大字号。
- **附带好处**：低分辨率让 rPPG / 人脸检测的**显示端开销几乎为零**，算力可以全给推理。

### 对既有方案的四处修正
1. **NFC 有，方案 C 转为可做**：MFRC522 是读卡器，可读 Mifare 卡/标签 → 「拿食物卡喂它」「碰卡切换用户/模式」完全可行。挂 I2C 或 UART（跳线可选），驱动成熟、移植风险低。
2. **不是陀螺仪，是加速度计（SC7A20H）**：文档里凡提"陀螺仪"应改为"加速度计"。影响很小——拿起、摇晃、轻拍、朝向都能测；但**不要**在答辩里说"陀螺仪/角速度"，会被专业评委抓住。
3. **双麦而非麦克风阵列**：2 颗麦只能解**左右一个轴向**的方位。但我们是左右双眼设备，"谁在左边说话就往左看"恰好只需要这个轴——**功能不缩水，宣传口径要准**（说"双麦声源定位/左右寻声"，别说"麦克风阵列 DOA")。
4. **双屏无触摸，J 方案（摸摸头）作废**：触摸只在单屏方案上。替代方案：**加速度计检测轻拍/抚摸动作** + **S1–S3 按键**，同样能做"被抚摸"的交互，且不依赖 TP。

### 原理图带来的三个新机会（推荐补进功能）
- **H. 「饿了要充电」养成闭环** —— 用 `ADC0` 读电量：低电量时眼神变虚弱、LED 转暗、主动"喊饿"；插上充电就恢复活力。把"喂养"和真实电量绑定，情感闭环自洽，几乎零成本。
- **I. 「拿起即醒」超低功耗待机** —— SC7A20H **支持睡眠唤醒**：平时深睡（屏灭、摄像头关），加速度中断一拿起就醒。既是拟人细节，又能在答辩里讲 **openvela 低功耗优化**（评分表「针对特定硬件能力深度优化」加分）。
- **J.（已作废）触摸交互「摸摸头」** —— 双屏方案无 TP，改由加速度计轻拍检测 + 按键实现。
- **K. 外设电源门控做低功耗** —— 方框图有**外设电源控制**：待机时给摄像头/屏/NFC 断电，仅留加速度计中断唤醒。配合"拿起即醒"，可在答辩里量化讲 openvela 低功耗优化（评分表加分项）。
- **L. 3D 打印"萌宠"外壳（性价比最高的加分项）** —— 大赛发**嘉立创打样券（PCB + SMT + 3D 打印，400 元）**，且 HDK 的原理图源文件就是**嘉立创 EDA（LCEDA）的 `.json` 格式**可直接编辑。评分表「技术难度」含**硬件工程能力**、「产品创新性」含**硬件形态设计创新**。
  → **优先做 3D 打印外壳**：把裸板变成有形态的桌面萌宠（双眼位置开窗、摄像头开孔、喇叭出声孔），路演观感提升巨大而投入很小。
  → **自制 PCB 视余力**：可基于 HDK `Reference design` 裁一版 VelaPet 专用小板。**务必等移植主线（M1–M3）跑通后再做**，不要抢占关键路径。

### 🎧 双麦寻声（A 方案）可行性 —— ⚠️ 前提：实物只装了 1 颗麦

**实物现状（已核对板子）**：两个麦克风座（丝印 M1 / M2）中**只有一个接了麦克风，另一个空置**；已装那颗用细漆包线引到**面板两眼正中**（居中拾音，对唤醒/命令词是最优位置）。

**因此：**
- ✅ **语音唤醒 + 离线命令词（核心功能）不受影响** —— 单颗居中麦克风完全够用。
- ⚠️ **双麦寻声（A 方案）需要自行补第二颗麦**：座子和驱动都现成（芯片支持 MIC1/MIC2 两路），但要采购一颗 2pin 模拟 MEMS 麦（`AM_065200-GML020` 或兼容品）并接到空置座上。

**若决定补第二颗麦**，TDOA 分辨力测算（声速 343 m/s）：

| 麦间距 d | 最大时延 | @16kHz | @48kHz |
|---|---|---|---|
| 9.4mm（紧贴座子） | 27 µs | 0.4 采样 ❌ | 1.3 采样 ❌ |
| 40mm | 117 µs | 1.9 采样 ⚠️ | 5.6 采样 ✅ |
| **60mm（推荐）** | 175 µs | 2.8 采样 | **8.4 采样 ✅** |
| 80mm | 233 µs | 3.7 采样 | 11.2 采样 ✅✅ |

**设计结论：**
1. **绝不能把两颗麦挤在座子旁**（9.4mm 无法判向）。好在麦克风是**细线外接**、现有那颗已能从底层边缘走到面板正中，说明**线长足够拉开到 60mm 以上**。
2. **拉开到 ≥60mm，装在 3D 外壳的"两只耳朵"位置** —— 造型语言与功能最优解一致，**L 方案（外壳）与 A 方案（寻声）在此咬合**。
3. **音频采样率取 48kHz**（16kHz 分辨力不足）。
4. 算法：**GCC-PHAT + 抛物线亚采样插值**，目标输出"左/中/右"3–5 档粗方位即可驱动眼球转向，不追求精确角度。
5. 双麦仅左右轴且存在前后镜像模糊 —— 对本设备无影响。
6. **外壳设计新增约束**：预留两侧麦克风安装位 + 走线通道，以及喇叭出声孔。

### 🔀 A 方案的取舍建议（重要决策点）
"转头看你"其实有**两条实现路径**，而摄像头那条**已经在核心功能里**：

| 路径 | 依赖 | 成本 | 可靠性 |
|---|---|---|---|
| **视觉眼神跟随**（人脸框 → 视线） | 摄像头（已有，且本就要用） | **零额外硬件** | 高；但需人在画面内、需有光 |
| 双麦寻声（TDOA） | **需补第二颗麦** + 拉开 60mm | 低（一颗麦）但要采购/接线 + 算法工作量 | 中；不受视野/黑暗限制 |

**建议：**
- **基线方案取"视觉眼神跟随"** —— 零额外硬件、效果直观，且摄像头本来就要打通（rPPG/人脸都要用）。
- **双麦寻声降级为"进阶增强"**：若能顺手买到一颗兼容麦，再加上去做**互补**——"**听到声音先转过去，再用眼睛确认**"（听觉引导视觉），这个组合叙事很有说服力，也解决了摄像头视野窄/黑暗的短板。
- **不要把双麦寻声放在关键路径上**，它不值得为此卡住进度。
